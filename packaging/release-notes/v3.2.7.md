## What's new in 3.2.7: see where frame generation goes wrong, and choose PushFlow's motion size

This version is the first step of PushFlow 2, the plan for the next generation of PushFPS's own frame
generation. Two things in it are for you to use. The rest is groundwork and measurements, and this page says
which is which.

**The frame generation quality test shows its worst frame and its worst place.** The test (*Frame generation
quality test*, also part of *Optimise for my PC*) withholds every second real frame of your game, lets frame
generation make it again, and compares the two. Until now it gave averages. When a fast object is left out of
a generated frame, or shown twice, the average hardly moves: the rest of the picture is fine. The result now
has two more lines:

- **Worst frame**: the least accurate generated frame of the test.
- **Worst place**: the picture is split into 144 tiles and the least accurate tile of each frame is taken. A
  missing object shows here clearly.

The score itself is calculated as before, so *Optimise for my PC* chooses what it chose before. This works
for every frame generation method, not only PushFlow.

**PushFlow: choose the motion size** (*Professional → PushFlow motion size*). PushFlow works the motion out on
a smaller copy of the picture and then rebuilds the new frame at full resolution from the real frames. Until
now the tier fixed that size: Fast 540p, Balanced 720p, Quality 1080p. You can now choose it yourself:
**Automatic** (as before), **540p**, **720p** or **1080p**, with any tier. The tier still chooses the model.

- A smaller size costs the graphics card less, and sometimes follows a fast object further. A larger size is
  more exact for small motion. Sharpness does not change, because the picture is always rebuilt from the
  full-size real frames.
- Which one suits your game can only be measured: change the size, run the quality test, and compare
  **Worst place**.
- The row shows the size PushFlow really runs at while you play, and the performance report includes it.
- If your card cannot keep up with a size you chose, PushFPS puts it back to Automatic and tells you, before
  it lowers the tier.

With **Automatic**, which is the default, PushFlow runs exactly as it did in 3.2.6.

**What we measured, and did not build.** PushFlow 2 has six parts. Before building them we measured the
models PushFPS ships, and several ideas did not hold. We would rather tell you than ship a switch that does
nothing:

- A fast object that PushFlow cannot follow is **left out** of the generated frame; it is not shown twice,
  and nothing inside the network marks the place. Two rules that were meant to detect and hide this acted on
  correct frames (fades) instead, so neither is in this version. One was built whole and taken out again
  before release.
- No motion size is best for every kind of motion, which is why it is now your choice and not a new automatic
  rule.
- Making each real frame's features once instead of twice could save at most 7 to 24 % of the network's
  arithmetic, depending on tier and multiplier. That needs measuring on real cards before it is worth a
  second model session.
- A frame *ahead* of the newest real frame can be made from what the network already gives, for slow motion.
  It needs much more before it can be shown in a game, and a camera before anyone may claim it lowers delay.

The full account, with the numbers, is in `docs/PUSHFLOW2.md`.

**Under the hood.** What PushFlow's models give besides their picture is now written down as code with its
own test, and the shader that rebuilds the full-size picture is checked against it pixel by pixel. A list of
protected features names the test that guards each one; a build fails when such a test is removed or no
longer run.

**How this was tested.** Every build is compiled and started on a Windows build machine without a graphics
card. In CI: the motion size rule for every tier and picture size, compared bit for bit with the 3.2.6 rule
when nothing is chosen; PushFlow through the real graph on Microsoft's software renderer with and without a
chosen size; the Fast tier at a chosen size against the Balanced tier at the same size (the same model, the
same picture); the too-slow rule from every starting point; the worst place on a picture with a missing
object (the whole picture 29.6 dB, its place 8.1 dB); the new rows in the QML tests; the install test. The
measurements above are from the shipped models running on a CPU, on drawn pictures.
**Not tested on real hardware**: the motion size has not been tried on a real graphics card or with a real
game, so we do not know yet which size is better for which game or card. That is what the quality test's new
lines are for. If PushFlow behaves worse with a chosen size, set it back to **Automatic**, and please send a
performance report (*Settings → Performance report*).

**Windows Defender note.** Defender may flag new PushFPS downloads as `Trojan:Win32/Tecabans.STV!cl`. This is a false positive from its cloud check on new, unsigned files, and it has been reported to Microsoft. Always check the zip against `SHA256SUMS.txt` on this page.
